## Section 1 — Fork Decision: Option A (Rust port)

**Decision**: Implement the LongMemEval scorer as a pure Rust port of `evaluate_qa.py`.
**User HITL gate**: 2026-05-28. Option A locked by user after research.
**Research basis**: `.ship/sessions/kremory-v014-phase1-20260528-074901/swarm-memory/P3-T1-fork-research.md`

### Summary

The LongMemEval scorer (`evaluate_qa.py`) is 110 LOC Python whose entire
scoring logic is:

1. Select one of 5 prompt templates based on `question_type` + abstention flag
2. Call an LLM judge with `temperature=0, max_tokens=10`
3. Parse `"yes" in eval_response.lower()` → binary label
4. Compute `mean(labels)` per `question_type` and overall

This is an exact match to kremory-eval's existing `Judge` trait pattern. The
Rust port uses `LongMemEvalScorer<J: Judge>`, where production uses `GemmaJudge`
and tests use `MockJudge`. Zero new Rust dependencies beyond what was already in
`Cargo.toml`.

**Options considered** (from research swarm, 2026-05-28):

| Option | Decision |
|--------|----------|
| A — Rust port (~80–100 LOC) | **SELECTED** |
| B — Python subprocess | Rejected: subprocess env adds reproducibility variables; no real benefit |
| C — PyO3 hybrid bridge | Rejected: ABI instability, build complexity, ~6h overhead |

## Section 2 — O4 Reconciliation: "5 abilities" vs "6 question_type values"

**Claim**: There is no discrepancy between the paper's "5 abilities" and the
dataset's 6 `question_type` values.

### Dataset ground truth

From `print_qa_metrics.py` @ `9e0b455`:

```python
type2acc = {t: [] for t in [
    'single-session-user',
    'single-session-preference',
    'single-session-assistant',
    'multi-session',
    'temporal-reasoning',
    'knowledge-update'
```

**6 named `question_type` values** in the actual data.

Abstention questions use one of the 6 types AND have `_abs` suffix on
`question_id`. Abstention accuracy is a cross-cutting derived metric, not a 7th

### Paper's 5 abilities → data mapping

| Paper ability | `question_type` values |
|---|---|
| Information Extraction | `single-session-user`, `single-session-assistant`, `single-session-preference` |
| Multi-Session Reasoning | `multi-session` |

| Abstention | Cross-cutting (any type + `_abs` suffix) |

### For kremory-eval

`per_type_accuracy` uses the 6 `question_type` keys (matches `type2acc`).
`abstention_accuracy` is reported separately as a derived metric.
`AbilityCategory` enum maps the 5 paper abilities for grouping if needed.

### Mem0 "6 categories" claim

Mem0's research paper and website (mem0.ai/research, verified 2026-05-28) report
LongMemEval performance across "6 categories" — this is correct and matches the
6 `question_type` values in the data.

## Section 3 — O6 Token-Efficiency Formula

**Source**: Mem0 research paper (arXiv 2504.19413) + mem0.ai/research
**Verified**: Research swarm 2026-05-28.

### Formula

```
mean_input_tokens_per_recall = sum(input_tokens_used per recall call) / count(recall calls)
```

`input_tokens_used` = the number of input tokens passed to the LLM to answer
each recall query (i.e., the context window consumed per question).

This is NOT a ratio formula (tokens recalled / tokens total). It is a raw
mean over per-query input token counts.

**Mem0 reported value**: 6,787 tokens mean for LongMemEval (vs 25,000+ for
full-context approaches, ~3.7× reduction).

### Implementation in kremory-eval

`LongMemEvalReport::mean_input_tokens_per_recall: Option<f64>` is computed as:

```rust
sum(score.metadata["input_tokens_used"] for all scores with Some value)
    / count(scores with Some value)
```

### Caveat: Mem0 open-source code does NOT contain LongMemEval scorer

**Verified**: `gh api repos/mem0ai/mem0/git/trees/HEAD?recursive=1` — zero files
with "longmem" or "long_mem" in path (2026-05-28). Mem0's `evaluation/`
directory evaluates LoCoMo only. The LongMemEval score (94.4) and token
efficiency (6,787) are from the research paper, not the open-sourced eval code.

### API gap: O10

kremory v0.1.0 `Memory::recall()` returns a `String` and does not expose token
usage. `LongMemEvalOutput::input_tokens_used` will always be `None` in the
adapter until kremory surfaces usage telemetry on its public API.

## Section 4 — Judge Non-Canonicity Disclosure

**Statement**: v0.1.4 LongMemEval scores are produced using a local Gemma 4
E2B Q4_K_M judge. The canonical evaluation per `evaluate_qa.py` uses GPT-4o
(`gpt-4o-2024-08-06`).

**Implications**:
- Scores are comparable-class but not bit-for-bit identical to published results
- Verdict divergence is expected on borderline cases where GPT-4o and Gemma 4
  disagree on "yes" / "no" interpretation
- kremory-eval's v0.1.4 baseline is labeled as "local-Gemma judge" throughout
  to prevent confusion with the canonical GPT-4o scored results

**Why accepted**:
- The trade-off is the same one accepted in Layer B (GemmaJudge for all
  model-graded metrics) — consistent within the eval harness
- An OpenAI API key would be needed for canonical scoring; kremory-eval is
  designed to be zero-cost and reproducible locally
- A future `--judge openai` option would enable canonical comparison

## Section 5 — API Gaps Surfaced (O8 / O9 / O10)

Discovered during `longmemeval_adapter.rs` implementation. These are gaps
between kremory v0.1.0 public API and LongMemEval adapter requirements. No
kremory crate changes were made (BYOM scope constraint respected).

| Gap ID | Description |
|--------|-------------|
| O8 | Per-session namespace isolation: adapter uses one `Namespace` per `question_id` to prevent cross-contamination. A future "ephemeral namespace" API would simplify adapter code. |
| O9 | No per-turn temporal anchoring: `Memory::remember()` accepts `.published_at(ts)` at episode level. LongMemEval sessions have per-session dates (not per-turn). Adapter sets `published_at` at session granularity. Per-turn temporal anchoring is not expressible in v0.1.0. |
| O10 | Token usage not surfaced from recall: `Memory::recall()` returns `String` only. No mechanism to retrieve input token count per call. `LongMemEvalOutput::input_tokens_used` is always `None` from adapter until kremory exposes usage telemetry. |
| O11 | Adapter not wired into eval.rs Gemma path — resolved Quinn cycle-2 (see Section 6). |
